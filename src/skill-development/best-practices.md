# 技能编写最佳实践

> 这篇文档总结了编写高质量技能的经验和建议。

## 核心原则

### 1. 单一职责

一个技能只做一件事。不要试图在一个技能中覆盖所有场景。

❌ **反模式**：一个"万能助手"技能试图处理所有请求
✅ **正确**：分别编写"代码审查"、"文档生成"、"数据分析"等独立技能

### 2. 触发条件明确

清晰定义什么时候应该使用这个技能：

```markdown
## 触发条件
当用户明确要求"审查代码"或"code review"时使用此技能。
```

### 3. 步骤可执行

每个步骤都应该是 AI 能直接执行的具体操作，而非模糊描述。

❌ **反模式**："分析代码质量"
✅ **正确**："检查以下 5 项：1) 空指针风险 2) 资源泄漏 3) 并发安全 4) 命名规范 5) 注释完整性"

### 4. 包含约束

明确告诉 AI 什么不该做：

```markdown
## 约束
- 不要修改用户未提及的文件
- 不要安装未经确认的依赖
- 遇到不确定的情况先询问用户
```

## 结构模板

```markdown
---
name: 技能名称
---

# 技能名称

一句话说明用途。

## 触发条件
什么时候使用。

## 前置条件
需要什么输入或环境。

## 操作步骤
1. 具体步骤 1
2. 具体步骤 2
3. 具体步骤 3

## 输出格式
期望的输出样式。

## 约束与注意事项
- 不要做什么
- 边界情况处理

## 示例
输入 → 输出 的具体例子。
```

## 测试验证

编写完技能后：

1. 在 CLI 中安装技能
2. 发起对话测试触发条件
3. 验证 AI 是否按技能指令行事
4. 测试边界情况

## 常见反模式

| 反模式 | 问题 | 改进 |
|--------|------|------|
| 技能过长 | 占用过多上下文窗口 | 精简为核心指令 |
| 缺少示例 | AI 理解偏差 | 至少包含 1 个示例 |
| 过于宽泛 | 误触发 | 明确触发条件 |
| 硬编码路径 | 不可移植 | 使用相对路径或变量 |
